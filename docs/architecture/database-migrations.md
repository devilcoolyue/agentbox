# 数据库迁移与回退

SQLite 使用 `PRAGMA user_version` 记录 schema。迁移按 `internal/store/migrations.go` 连续编号执行；SQL 在 `internal/store/migrations/`。一次打开需要应用的所有迁移与版本更新在同一事务中提交，语句失败或进程中断不会留下半套表结构。

| 版本 | 内容 |
| --- | --- |
| 0 | 未版本化的旧数据库；可能已具有部分后加列 |
| 1 | 建立基线并检查补齐旧列、索引，保留已有用户/空间/用量/额度 |
| 2 | usage_events.price_snapshot，旧行留空，新行保存计价来源与两档价格 |
| 3 | 将既有用量时间规范化为固定精度 UTC；新记录与筛选边界使用相同格式，保证跨时区排序和日期筛选正确 |
| 4 | 用户 Git 提交身份 |
| 5 | Git 连接、空间/用户默认、仓库绑定与操作审计 |
| 6 | Git 操作结束时间 |
| 7 | Git 连接的不可变网络路由与公司 CA |
| 8 | 共享 Git 服务账号的用户读写授权 |
| 9 | usage_messages 按工作空间和 Claude 消息 ID 持久去重；与用量、额度同事务提交，不改历史费用 |
| 10 | client_projects/client_terminals：桌面逻辑目录映射、启动参数、修订号与稳定终端 ID；不改变空间账号/模型，不移动文件 |
| 11 | workspace_creations/workspace_imports：按用户创建身份隔离的创建/导入收据，保留删除后的重放阻止记录；不修改既有空间、用户密码、用量或额度 |

| 13～16（开发预览，已由 18 删除） | 旧“多 Agent 协作”的任务、参与者、步骤、交接、对话绑定、决策尝试与评审证据表；生产开发预览 `.15` 曾使用 16。schema 18 迁移整体删除这些表与触发器，旧任务不保留。 |
| 17 | usage_events 增加 effort / effort_control，保存终端日志中实际记录的推理强度；旧行默认留空，扫描现存原始日志后原位补齐，不拆分旧行、不改历史价格或余额。 |
| 18 | 主管委派：删除旧协作参与者会话及全部协作/决策尝试表与触发器；新增 delegation_workers（属主空间 × 账号的隐藏跑腿会话）、delegations（每次委派的冻结任务、路由、跑腿绑定、状态、报告、改动与主 Agent 评价），usage_events 增加 delegation_id。历史用量、价格与余额不变。 |
| 19 | 对话跟进：按 rowid 顺序重建 chat_requests，状态增加 `queued`（回合运行中发来、排在其后执行，不占每空间唯一的活动名额），新增 `merged_into`（引导消息交给的运行中请求 ID）与排队索引。既有回执原样复制，修订号、ID 围栏和活动唯一索引不变。 |
| 20 | 每次请求的实测计时：`usage_events` 新增 `api_request_id`（provider 请求 ID，带部分索引）、`api_ttft_ms`、`api_duration_ms`；新增 `request_timings`，按 (用户, 请求 ID) 暂存先于用量行到达的 CLI 遥测计时，用量行写入时取走，72 小时内未对上的清理。只加列加表，既有行与账本不变；升级后重扫的终端行补上请求 ID。 |
| 21 | 缓存保活：新增 `workspace_keepalive`（每个空间一行：是否开启、是否连同终端会话、空间自己的最长时长与上下文门槛，0 跟随管理员默认值）。没有行即未开启；删除空间或用户时同事务删除。只加表，既有数据不变。 |
| 22 | 五小时额度暂停：`workspace_keepalive` 增加 `pause_percent`（0 跟随管理员默认值，-1 关闭）；新增 `account_rate_windows`，每个 Claude 订阅账号保存最近一次回复报告的五小时窗口用量与重置时间，使暂停在重启后保留。只加列加表，既有数据不变。 |
| 23 | 终端计费：`usage_events` 增加 `settled_micro_usd`（该行已结清的金额，终端行重写时只扣增长部分），迁移时已有的终端与后台行记为已结清、不追扣；新增单行表 `terminal_billing` 记下启用时刻，早于它的请求只记不扣。只支持 22 或更低版本的二进制无法打开新库；回退须恢复升级前兼容备份，升级后的终端扣款流水不会保留。 |
| 24 | 并行线程：`chat_requests` 的活动唯一索引从每空间一条改为每（空间，线程）一条，排队索引加上线程，使同一空间的线程各自运行、各自排队。只改索引，既有回执原样保留。只支持 23 或更低版本的二进制无法打开新库；回退须恢复升级前兼容备份。 |

v0.1.13 使用 schema 18；上一正式版 v0.1.12 使用 schema 12，上一生产开发预览使用 schema 17。升级前应取得并验证与当前版本匹配的兼容备份；升级后只支持 17 或更低版本的旧二进制无法打开新库。迁移会删除旧协作任务及其参与者空间记录，参与者容器与磁盘目录由运维另行清理，不在迁移事务内删除宿主机文件。委派记录随数据库备份；恢复后的实例启动时把未结束的委派标为 uncertain，不自动重跑。回退须恢复升级前的兼容备份到新目录。设计与边界见[主管委派](delegation-supervisor.md)。

v0.1.14 使用 schema 19，从 v0.1.13 升级只执行 18 → 19，从 v0.1.12 及更早升级连续执行到 19。v0.1.13 等只支持 18 或更低版本的二进制无法打开新库；回退须恢复升级前的兼容备份到新目录，升级后排队而尚未执行的消息不会保留。

v0.1.17 使用 schema 22，从 v0.1.14～v0.1.16（schema 19）升级执行 19 → 20 → 21 → 22，开发预览从 20 或 21 接着执行。只支持 21 或更低版本的二进制（含 v0.1.14～v0.1.16）无法打开新库；回退须恢复升级前的兼容备份到新目录，升级后记下的实测计时、缓存保活设置与暂停状态不会保留。

v0.1.18 使用 schema 23，从 v0.1.17 升级只执行 22 → 23，更早版本连续执行到 23。只支持 22 或更低版本的二进制（含 v0.1.17）无法打开新库；回退须恢复升级前的兼容备份到新目录，升级后的终端扣款流水不会保留。

当前开发版使用 schema 24（并行线程），从 v0.1.18 升级只执行 23 → 24。只支持 23 或更低版本的二进制（含 v0.1.18）无法打开新库；回退须恢复升级前的兼容备份到新目录，升级后接收的回执与排队消息不会保留。

v0.1.11 首次启动将 schema 10/11 升至 12。schema 12 的聊天存储层已接入 HTTP v1 与原执行器；浏览器现已接入冻结待确认副本、查询优先恢复和显式核对。服务初始化在连接 Docker 前，将残留 accepted/starting/running 聊天回执改为 uncertain；不从这些记录重放任务。状态转换使用修订号，旧执行者不能覆盖重启恢复后的记录。会话创建和默认 Git 绑定与收据完成仍在同一事务提交；文件发布与数据库之间不是一个事务，无法确认的导入保持 uncertain，须人工核对后继续。服务重启将残留 running 导入改为 uncertain，不自动重跑。

升级前应取得并验证备份。v0.1.10 等只支持 schema 10 的二进制、以及仅支持 11 的旧开发二进制不能打开 12；回退要恢复兼容备份到新目录，已演练的步骤见[从 v0.1.11 回退到 v0.1.10](../compatibility.md#从-v0111-回退到-v0110)。默认系统备份包含收据：聊天回执一旦接入发送会保存已接收的提示词、模型/推理选项和附件引用，但不包含附件或项目文件，完整文件恢复仍须 full 备份。删除空间/用户时同事务清空聊天请求正文并保留 ID 围栏；删除线程先清空对应正文并保留围栏，再删除转录；这不是对旧备份或数据库空闲页的物理擦除。离线密码恢复也应使用与实际 schema 匹配的二进制，不通过恢复密码命令顺带迁移。

schema 10 的项目映射只保存元数据，工作空间删除时同事务移除相关项目与终端行。终端先保存
`closing` 状态再结束远端 tmux，失败可重试，重启不会把正在结束的终端当成可连接对象。
默认系统备份包含这些表；文件仍需完整备份。回退到只支持 schema 9 的二进制前必须恢复兼容
备份到新目录，并另行保全升级后发生变化的文件，不能直接打开已迁移的数据库。

v0.1.3 使用 schema 8，可从 v0.1.2 的 schema 3 自动升级；新建 Git 表和索引，不删除已有空间、用户、用量和额度。迁移后旧版本不能直接打开数据库。Git 密钥目录须与配置、数据库一起备份，执行过密钥轮换后还须保留配套版本化 keyring。

打开数据库首先读取版本，超过当前支持的版本就报错退出，不建表、不降级，也不先切换 WAL。接受的数据库完成迁移后继续使用 WAL，运行连接使用 synchronous=FULL（包括重新建立的连接），让每次提交同步 WAL 后再返回；实际耐久性仍依赖文件系统与设备正确实现同步。此设置会增加写入等待，需要在目标 Linux 磁盘验收吞吐；没有改变用量和扣款的事务边界。首次启动仍支持导入旧 state.json；已有 SQLite 行优先，成功导入后原 JSON 改名留存。

升级前用旧程序可用的备份方式取得并验证备份，保留原配置和数据副本。新版首次启动自动迁移，无需手工 ALTER TABLE。不要人为改小 user_version 或删除列来“强行兼容”，这会绕过版本保护。

旧版本程序可能根本没有版本检查，不能保证它会拒绝打开新库。尤其旧版终端扫描可能重新计算价格且不保留快照。**回退应停服务后恢复兼容备份到新目录，并使用与之匹配的二进制/配置**；不要拿旧程序直接访问已升级库，也不要混用旧 WAL/SHM。账号授权的回退限制仍然适用。

验证覆盖：最早旧会话表、完整未版本化库、版本 1 到 3、重复启动、高版本拒绝且文件未改动、SQL 失败及子进程在迁移事务中直接退出后的恢复。版本 2 的价格快照、用量和额度流水仍同事务写入；坏快照序列化失败会回滚本批用量与扣款。版本 3 只改变时间的存储表示，不改变记录代表的实际时刻、用量或扣款。
