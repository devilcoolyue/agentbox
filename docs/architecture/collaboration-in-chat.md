# 在空间对话中使用多 Agent 协作

[文档导航](../README.md) · [协作底层设计](agent-collaboration.md) · [当前实现](../collaboration-preview.md)

状态：同对话协作、补充要求与结果应用已形成可测试实现，尚未发布。2026-10-11。本文基于当前工作树评估，不代表生产已支持。已有双角色调度、交接、快照、验证与计费继续复用；本轮重点是让协作成为空间内的一种消息执行模式。

## 1. 产品决策

用户始终在同一个空间、同一条对话中工作。在发送前选择「普通对话」或「多 Agent 协作」，发送后在当前消息流里查看计划、交接、问题、进度和结果。空间创建时无需决定以后是否使用协作。

设计主旨：延续现有聊天工作台的安静底色和单一强调色，用清晰的角色、状态和留白表达协作。

内容层次：对话为主；输入框负责需求与执行方式；任务消息负责进度与下一步；侧栏负责团队、详细记录与画布。常态不另设任务首页。

动效主旨：模式选中标识轻量过渡；任务阶段更新局部淡入；画布展开后仅当前活动节点和真实交接方向出现动效。暂停、隐藏及减少动态效果时停止持续动画，不打断滚动或输入。

首期两个模式即可，不增加“自由群聊”“辩论”“任意并行”等尚无调度能力支撑的选项。界面名称用“执行方式”；Agent 的通信由协作流程负责，用户不需要配置通信协议。

## 2. 当前割裂的根源

| 代码现状 | 用户感受 | 调整 |
| --- | --- | --- |
| `index.html` 的侧栏按钮打开 `panel.ts` 独立 dialog，内部另有任务列表、需求输入和项目选择 | 像进入另一套产品，要重新说明任务 | 主入口移到聊天输入框；移除独立侧栏入口，异常任务从消息内“更多操作”进入管理 |
| `CollaborationCreateInput` 只有源空间，没有对话关联与对话上下文 | 前面聊好的需求不能自然接着执行 | 冻结来源对话和上下文，任务持久绑定对话 |
| `chat.ts` 的发送只进入普通聊天路径 | 无法在发送同一段需求前选择协作 | 一个发送入口，按冻结的执行方式路由 |
| 计划确认、用户问题、实时记录只在协作面板 | 要离开聊天才能推进任务 | 交互投影到当前对话，画布和详情按需展开 |
| 交付只支持查看差异和下载独立快照 | “完成”后当前空间的代码仍没变 | 增加明确的结果应用流程与应用状态 |

仅把现有弹窗入口搬到输入框，无法解决后四项。

## 3. 页面与操作

```text
当前空间 / 当前对话                            [空间任务]

我：按刚才讨论的方案实现登录流程。

协作 · 规划 Codex / 执行 Claude Code
  规划中 · 正在梳理改动范围
  [查看过程] [本步结束后暂停]

Codex · 规划
  1. ……
  2. ……
  [确认并执行] [调整要求]

┌─────────────────────────────────────────────────────┐
│ 输入需求……                                          │
│ [多 Agent 协作 ▾] [Codex → Claude Code · 设置] [发送]  │
└─────────────────────────────────────────────────────┘
```

### 3.1 发送前

- 新对话默认“普通对话”；已有草稿恢复其执行方式，模式切换保留文字和附件。切空间、切线程不串配置，不把上一空间选择隐式套给新空间。
- 普通模式显示当前空间的模型/强度选择器；协作模式显示紧凑的团队摘要。点击摘要打开小型设置面板，分别选择规划/评审者和执行者的 Agent、账号、模型与强度，支持交换整套角色配置。
- 初次使用优先以当前空间已获授权的账号与所选模型配置规划者，另一角色使用可用选项；不强制 CC 主、Codex 辅。同类型组合也可用。后续恢复本空间最近使用且仍有效的团队配置，不跨空间继承账号选择。
- 项目固定为当前空间。仓库路径自动复用该空间已确认的路径；只有一个可用仓库时显示识别结果，多个候选时让用户选择，不能盲选。路径、验证命令、预算和自动执行放进展开设置。
- 显示“携带本对话上下文 · 查看”，允许改成只使用本次需求。上下文预览明确截取范围和附件支持情况；用户不用重新复制一遍讨论。
- 默认先确认计划，允许显式启用“规划后自动执行”。发送前始终能看到当前执行方式和团队摘要。
- 不支持协作的服务端/账号显示原因；绝不把协作需求静默发成普通聊天。发送预检失败时保留草稿，在输入框附近给出可操作错误。

### 3.2 发送后

仍留在当前对话，需求只出现一次。下面生成一个稳定的协作任务块，展示当前阶段、角色、最近一条有效进展和当前可执行动作。

“查看过程”在桌面展开右侧面板，包含“交流 / 画布 / 变更”；窄屏使用同一任务的详情层，返回后恢复原滚动与草稿。画布以后可扩展缩放和平移，但主流程不依赖画布操作。

消息流按任务分组展示有意义的交流：规划、执行者问题、规划者答复、评审意见和结果。每条标明实际 Agent 与职责，不把所有消息显示成一个匿名助手。详细工具调用与流式输出默认折叠；不暴露或虚构原始内部推理。

计划、待答问题出现时，在任务块中突出下一步，不强制切页或滚到底部。顶部可以提示“有任务需要处理”，点击才定位。SSE 增量只更新已有节点，历史轮询不重建输入框或重播动效。

### 3.3 一个输入框，发送目标明确

“执行方式”和“回复哪个任务”是两个不同维度。任务运行中不能凭一段自然语言猜测用户是答复、补充要求、普通聊天还是新建任务。

| 场景 | 输入框行为 | 后端语义 |
| --- | --- | --- |
| 无活动任务 | 可选普通/协作 | 创建普通回合或协作任务 |
| 等待用户答复 | 点击任务里的“答复”，显示“回复此任务”及问题摘要 | 使用当前 `pending_question` 的 `answer` 动作 |
| 等待计划确认 | 直接在计划下确认；调整要求则进入任务补充模式 | 确认绑定计划版本；补充触发新规划 |
| 执行中补充要求 | 显示“补充给此任务”；接受后标注“等待当前步骤结束” | 新增持久补充动作，到安全边界纳入规划 |
| 想单独聊天 | 明确选择“普通对话”，退出任务回复目标 | 原空间普通聊天路径，不向协作伪装答复 |
| 想另起协作任务 | 使用“新建协作任务”明确退出旧目标 | 首期同一对话最多一个未结束任务；提示先结束或新建对话 |
| 任务结束 | 清除回复目标，恢复普通对话并显示模式 | 不因用户输入“谢谢”自动新建协作任务 |

进入任务答复时保留此前未发草稿；退出答复恢复原草稿，任务答复草稿按 run/question 隔离。问题版本变更后保留文字供用户核对，但禁止继续发送到已失效问题。

运行中调整团队依旧先申请在当前步结束后暂停，确认旧参与者停止后更新配置代际。补充要求不能修改正在执行的冻结输入；到边界后生成新计划，按任务的确认策略推进。部分完成的代码与费用保留。若补充到达时任务已结束，返回明确冲突，让用户选择后续任务，不能偷偷丢弃或重开。

停止按钮必须标明目标。普通对话沿用中断；协作默认“本步结束后暂停”，立即取消放进任务操作。发送模式切换不取消已提交任务，也不把协作暂停画成普通对话断线。

### 3.4 同一空间的文件与结果

前台统一空间，后台继续使用独立角色上下文和任务副本。不能为了页面看起来统一，就让两个 CLI 并发写同一份项目或互相复制登录信息。

结果呈现分两步：

1. **评审通过，结果待应用**：在对话中展示总结、验证结果、文件差异，提供“应用到当前项目”和下载入口。
2. **已应用到当前项目**：显式应用成功后刷新文件/变更视图，在同一对话继续提问和开发。

“应用”必须是新实现的受控操作：核对源仓库仍与冻结基线一致、没有未提交修改，检查空间所有写入入口及运行进程，展示差异后由用户明确提交。源项目变更时拒绝覆盖并解释冲突；首期不自动解决冲突或强制回退。应用后改动保留为当前项目的未提交变更，不自动 commit/push/deploy。

所有源空间写入与应用共用准入，包含聊天、终端、文件 API、Git 和后台进程；仅锁住网页按钮不足以保证安全。实施前需明确跨文件写入的暂存、恢复清单和崩溃处理。未完整确认成功的应用标为待核对，查询不能重写文件。恢复不得覆盖应用失败后用户新改的内容。

协作期间允许继续普通对话，但提示“当前项目与协作副本可能不同”；源空间产生新修改后，原结果不能无检查应用。阶段一没有结果应用能力时，必须继续显示“待应用 / 下载”，不宣传已完成空间内交付闭环。

## 4. 上下文衔接

### 4.1 普通聊天转协作

创建前取得服务端确认的来源线程标识与历史边界。冻结本次需求、该边界之前的用户/助手可见内容、用户选择的上下文范围、项目路径及基线摘要。只读取属主有权访问的当前对话，不抓取同空间其他对话。

首期采用有界的可见对话片段，不额外调用付费模型生成“记忆”。明确展示截断和省略，允许用户补充遗漏约束；后续若引入摘要，须记录摘要来源、版本和费用。历史工具结果、原始推理、凭证与整个终端输出不自动进入材料。

附件需要重新验证归属并复制到任务拥有的受限材料目录，具有清单、摘要、总量限制与清理规则，生命周期跟随任务而非聊天附件的 48 小时 TTL。未实现相应类型前，保留附件并明确阻止提交或要求用户移除，不能静默丢失或只拼宿主机路径。

不同 Agent 通过这份材料衔接语义；Claude 的 provider 会话 ID 不传给 Codex，反向也一样。界面可显示“已携带本对话的上下文”，不能承诺完整继承另一模型的原生记忆。

### 4.2 协作结束后继续普通聊天

任务总结、关键决策、验证状态、结果快照和“是否已应用”成为当前线程的结构化引用。后续普通回合显式组装该引用对应的可见材料，不能只在页面显示而模型实际收不到。

引用附带 `run_id / revision / snapshot_id`；按当前授权解析，不把可变的“最新结果”悄悄替换进已冻结请求。任务删除或产物缺失后返回不可用标记。新回合明确区分协作副本与源项目，避免模型以为文件已经应用。

## 5. 技术落点

### 5.1 前端拆分

当前已落地：输入框执行方式与内联团队设置、线程上下文快照、schema14 线程关联、稳定消息锚点、计划确认、同输入框答复/补充、安全边界重新规划、侧栏交流/画布/差异，以及显式应用结果和中断恢复。独立侧栏入口已移除，任务消息保留过程与结果入口，异常状态的“更多操作”保留管理面板；历史任务显式关联、新线程复用最近团队、协作附件材料复制暂未实现，附件会明确阻止提交并保留。

| 位置 | 调整职责 |
| --- | --- |
| `internal/web/static/index.html`、`web/src/chat.ts` | 加执行方式、团队摘要、任务回复目标；统一鼠标、Enter 和语音完成后的发送入口 |
| `features/chat/draft-store.ts`、`drafts.ts` | 草稿升级，保存执行方式、配置引用、上下文选择和回复目标；旧记录默认普通对话；保留用户关闭本机保存的语义 |
| 新 `features/collaboration/client.ts` | 从 `panel.ts` 抽离 options、创建/动作、查询恢复及事件订阅，不依赖 dialog DOM |
| 新 `features/collaboration/composer.ts` | 模式与团队配置、预检、冻结输入、发送目标校验；不直接控制模型执行 |
| 新 `features/collaboration/thread-view.ts` | 任务消息、计划确认、待答问题和结束结果在聊天中的投影 |
| `workflow.ts`、`live.ts`、`evidence.ts` | 复用画布、实时过程和差异，挂入任务详情面板 |
| `panel.ts` | 保留旧任务查看与恢复入口，逐步成为“空间任务/全部任务”归档视图 |

不把整个 `panel.ts` 塞进 `chat.ts`，也不新增另一份协作状态机。UI 根据服务端动作能力和状态展示按钮，`revision` 保证状态单调。

### 5.2 服务端与存储

本次新增 schema 14；不修改已经用于生产的 013 迁移。新增 `collaboration_threads`、`collaboration_supplements`、`chat_collaboration_context` 和 `collaboration_applications`，对应以下实体：

- 对话关联：任务、属主身份、源空间、来源线程、稳定的消息锚点、创建请求 ID。
- 上下文材料：来源历史边界、材料清单与摘要、截断信息、正文/附件受限存储引用。
- 对话投影：任务创建/状态引用的稳定 ID、单调序号、删除围栏；重启后可从持久记录重建。
- 补充要求：动作 ID、接收修订号、正文、待纳入/已纳入状态、采用的计划版本。
- 结果应用：动作 ID、源基线、结果快照、应用状态、恢复清单与核对结果。

协作创建沿用持久幂等准入，加入版本化的线程/上下文引用，进入请求指纹；旧版独立任务请求继续按原语义处理。服务端返回能力声明，旧客户端不会把新字段或新状态当作普通聊天。

创建与对话关联应在同一个 SQLite 事务接受。聊天 JSONL 与 SQLite 不能假装是同一事务：任务事实以 SQLite 为准，聊天显示通过带稳定锚点的投影合并；如写入 JSONL 引用，必须使用持久待投影记录与去重恢复。不得先发一次普通聊天，再把同一条需求发给协作。

历史聚合需给普通消息和任务锚点稳定顺序与分页游标，覆盖空对话、向上翻页、跨设备及重启；不能按浏览器当前加载的消息临时猜插入位置。线程列表、标题和未读只统计一次用户需求。

空间任务接口支持服务端按空间/线程过滤并核对属主，不能只让前端取所有任务后过滤。删除有未结束任务的线程要先显式处理任务；不能因删除聊天而让不可见任务继续花费。已结束任务删除线程时撤销线程上下文及附件引用，任务按既定保留/删除规则处理。用户和空间删除、备份恢复同步覆盖新增材料和投影。

### 5.3 发送与恢复

统一入口不等于复用普通聊天的执行资格。发送前冻结 `mode / session / thread / team / text / context / refs / reply_target`：

- 普通消息仍进入原 chat outbox 与持久回执。
- 协作创建与动作进入协作请求存储，持久记录完整冻结输入；现有只在 sessionStorage 记录一个 pending ID 的方式不足以支撑多个线程。
- 根据实例/用户身份隔离，遵守本机保存开关和正文 TTL；不同模式的 pending 记录保留各自的协议和查询路径。
- 同一请求 ID 只能对应一个模式和固定输入。响应丢失只查询原 ID，不换 ID、不切协议重发；接受后清除对应的冻结草稿，保留用户期间新输入的内容。
- 刷新、SSE 重连、打开详情、切换空间仅查询。迟到结果必须核对登录身份、空间、线程和输入代际。
- 任务运行过程投影不再调用模型，不重复产生用量记录。任务费用沿用原 turn/usage/ledger，不能把每条可见交接当作新收费回合。

## 6. 旧任务与分步交付

旧任务只有源空间，不能自动编造历史线程归属。保留在对应“空间任务”中；用户可显式“关联到当前对话”，形成一个当前时刻的任务引用，不伪装成过去已发送的消息，也不重跑任务。

| 阶段 | 可验收结果 | 完成界限 |
| --- | --- | --- |
| A：统一入口与对话 | 输入框选择普通/协作，团队设置，持久线程关联，有界上下文，任务消息、计划确认、答复、刷新恢复、旧任务入口 | 必须一起交付，不发布只会弹出旧工作台的模式按钮；结果仍明确待应用 |
| B：运行中交流 | 同一输入框补充要求，安全边界重新规划，角色设置与暂停/恢复，按任务查看双方交流 | 需新增持久动作及其竞态测试，不用提示词假装热修改执行中任务 |
| C：项目闭环 | 差异预览，显式应用结果，冲突拒绝、崩溃核对，应用后继续对话 | 文件/变更视图与应用收据一致后，才称为完整空间内闭环 |

画布作为 A 阶段的详情视图复用现有实现，其后再单独增强；无需先重写画布才能统一体验。任意多角色、并行写入与可编辑 DAG 另行设计。

## 7. 验收场景

1. 普通对话讨论需求 → 切协作 → 查看携带材料 → 选择任意主辅与模型 → 发送；全程不离开空间，对话里只出现一次需求。
2. 两种模式之间切换保留输入和附件；键盘发送、按钮发送和语音完成采用同一冻结模式。旧服务端不支持时明确阻止协作提交。
3. 计划确认、待答问题、补充要求、暂停与模型切换都命中正确 run、question、plan 与 revision；两个浏览器竞争提交时只有一个获得执行资格。
4. 创建响应丢失后刷新、切线程、重新登录与查询恢复不重复启动模型；原有普通聊天的待确认、草稿、分页、用量回归继续通过。
5. 历史分页不会重复/丢失任务锚点；Agent 输出迟到不会进入其他空间；已删除线程和任务不残留可访问正文/附件。
6. 结果应用遇到源项目新修改、运行进程、撤权、服务崩溃与部分写入时不宣称成功；成功应用刷新文件视图，后续模型看到准确的应用状态。
7. Chromium / WebKit，简中/繁中/英文，六种皮肤及窄屏、键盘、减少动态效果覆盖；轮询不抢焦点，折叠过程不刷屏。
8. 合成后端浏览器链路核对实际执行次数、回执和账本；真实 Docker 文件/写入互斥单独验收。真实 provider 验收独立报告，不用模拟结果替代。


## 当前实现与验收边界

- 对话上下文取服务端确认的当前线程可见用户/助手消息，最多 24000 字节，包含选择开关、文件行边界和摘要。创建时重新核对，不接受客户端伪造正文或已过期预览；Claude 工具结果和思考不进入材料。来源附件不隐式引用，暂要求移除或用普通对话。
- 对话中的协作记录由 SQLite 线程锚点投影，保留原 JSONL 分页游标；任务需求只显示一次。一个线程只允许一个未结束任务；删除线程前需先删除关联任务，避免孤儿执行。历史任务暂保留原查看入口，不自动猜线程。
- 普通聊天在持久接收事务内冻结最近 8 个关联任务各最近 4 条交接（每任务最多 12000 字节），作为后续模型输入的附加材料，不改用户正文、回执指纹或计费路径。任务删除会撤销未执行回合对其材料的引用。旧 WebSocket 发送路径没有这项持久上下文增强。
- 补充要求使用幂等 `supplement` 动作；已有步骤输入保持不变，正常步骤完成后更新配置代际、重新规划。执行失败、费用不全、预算耗尽等状态继续要求原恢复流程，不能因补充要求绕过。没有新建额外的计费路径。
- 应用要求源空间停止、无活动/待核对聊天、Git 基线匹配且干净。先复制完整工作区（最多 512 MiB/50000 条目），保留 Git 元数据与忽略文件，再在暂存副本核对和应用快照，最后切换目录并同步；不提交、推送或部署。应用也受现有存储额度约束。
- 应用回执在切换前持久化；读文件可用，写入和启动在未确认应用期间被围栏阻止。刷新/查询不重复写。恢复在三个切换边界均保留原项目；已经切入的结果移为核对副本。恢复或失败后可显式以新的操作 ID 再次申请应用，旧 ID 只查询/重放原回执；原请求未接收时先登记放弃围栏，迟到请求不能落盘。
- 原项目副本位于会话目录内 `collaboration-before-<action_id>`，不挂入容器；恢复时另存 `collaboration-review-<action_id>`。副本受用户存储额度计量，随会话清理；目前没有单独的副本清理按钮。
- 待确认操作按实例/用户草稿范围及空间/线程隔离，关闭本机保存后仅保留当前页面内存；超过 7 天清正文保留查询标识。已确认的创建只清除仍与冻结内容相同的草稿。切空间、切线程和退出使迟到结果失效。
- 目前后台采用串行双角色调度。画布是只读进度视图，节点可以定位交流记录；不代表支持任意 DAG 或并行 worker。
