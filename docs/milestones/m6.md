## M6-05 WebKit 回归

`scripts/playwright-launch.mjs` 统一四个核心场景的浏览器启动：默认仍为 Chromium，`AGENTBOX_BROWSER_ENGINE=webkit` 切换引擎，断言不变。统一入口新增 `browser-webkit` 组（`webkit.browser`、`webkit.onboarding`、`webkit.chat-drafts`、`webkit.chat-outbox`），并加入 `release-full`。

本机环境：Debian 12 x86_64、Playwright 1.64.0 / WebKit 27.2（headless WPE）。本机无 root，WebKit 系统库从 Debian 12 软件包解到私有目录加载，仅影响本机运行方式；托管 runner 用 `playwright install --with-deps webkit`。CI 新增独立 `web-webkit` job（Playwright 1.58.2，与 Chromium 组版本一致），尚未在托管 runner 运行。

首轮 WebKit 运行中首次使用与草稿通过，待确认发送与主控制台失败。逐项判断后的处理如下，没有发现需要修改产品代码的 WebKit 缺陷：

| 现象 | 判断 | 处理 |
| --- | --- | --- |
| 待确认：输入框工具栏第二个按钮尺寸为 0 | 语音按钮在没有 Web Speech API 时按设计隐藏；Playwright WebKit 不提供该 API（真 Safari 提供） | 断言按能力分支：Chromium 必须有 Web Speech 且三个按钮一致；没有时语音须隐藏、其余两个一致 |
| 待确认：`newCDPSession` 不可用 | “冻结旧标签页后迟到的退出登录”用 CDP `Page.setWebLifecycleState` 冻结页面，只有 Chromium 有 | 非 Chromium 只跳过这一段并打印说明，其余照跑 |
| 主控制台：reload 时出现 `Fetch API cannot load … due to access control checks` 页面错误 | WebKit 把被 reload 取消的 fetch 记为控制台错误，Playwright 报成 pageerror；`refreshAll` 已捕获这些拒绝 | 仅 WebKit 下忽略这条精确文本 |
| 主控制台：保存模型能力后固定等 150 ms 即断言 | 固定等待的竞态，WebKit 更慢 | 改为最多 5 秒等待写入，断言值不变 |
| 主控制台：`clipboard-write` 权限未知 | Playwright 只在 Chromium 支持该授权；WebKit 写剪贴板无需授权、读取需 `clipboard-read` | 按引擎授权，仍读取真实剪贴板核对内容 |
| 主控制台：终端触摸回归 | 依赖 CDP 派发真实触摸 | 非 Chromium 跳过并打印说明 |
| 响应式：后退后分区标签仍是旧值 | URL 先变，hash 处理器稍后重绘 | 改为等待标签文字出现，仍须变为“提交身份” |

因此 WebKit 组**不覆盖**：语音输入入口、冻结标签页的迟到退出、终端触摸滚动与长按粘贴；这些仍只由 Chromium 组覆盖，真机 Safari / iOS 归 M10。

证据（本机统一入口）：

- `output/verification/20261008T120816Z-baeb18f3/`：`browser-webkit` 4 项通过——主控制台 258.5 秒、首次使用 172.2 秒、草稿 80.4 秒、待确认发送 96.4 秒。
- `output/verification/20261008T115753Z-bbf4cefa/`：改动后 Chromium `browser` 组 9 项全部通过（主控制台 204.8 秒、首次使用 118.4 秒、草稿 61.0 秒、待确认发送 77.7 秒）。Chromium 断言没有放宽：引擎分支只在非 Chromium 生效，两处条件等待对两种引擎相同。

两份报告都标记运行期间源码摘要变化：期间只编辑了本记录文件，测试脚本与产品代码未变。

## M6-07 回滚演练

`scripts/test-rollback-drill.py`（`verify.py --step release.rollback`）用两个真实 Linux 发布包和各自包内的 `deploy/release.py`，在隔离临时目录中演练：

1. 用 v0.1.10 的 `release.py` 安装并激活 v0.1.10，通过 API 建用户、两个空间、额度与充值流水、上传文件，并写入合成工作区文件与聊天记录。
2. 用 v0.1.10 的 `release.py` 安装、激活 v0.1.11：激活前由 v0.1.10 生成兼容备份，数据库 10 → 12，空间与文件可读。之后再建空间、上传文件、充值，模拟升级后的变化。
3. 用 v0.1.11 的 `release.py` 直接激活 v0.1.10：停服前被拒绝，`current` 与服务保持不变。
4. 按[兼容矩阵的回退步骤](../compatibility.md#从-v0111-回退到-v0110)回退：停服、用 v0.1.11 保留升级后状态、v0.1.10 直接打开升级后的库被拒且库未被修改、v0.1.10 校验并恢复兼容备份到新目录、移动用户文件、改写配置后由 v0.1.11 的 `release.py` 激活 v0.1.10。
5. 核对：schema 回到 10；用户、额度、账本、用量表及升级前空间的规范摘要与升级前一致；升级后新建的空间不在列表中但目录保留；升级前后上传的文件均可通过 API 读取；余额为升级前的 5,000,000 微美元（升级后充值按预期丢失）。

结果（最终脚本 `output/verification/rollback-drill-20261008T121912Z/`；此前各版本脚本的 `113636Z`、`115800Z` 与统一入口 `20261008T113813Z-52ec8b37/` 同样通过，回退合计 4.9～5.5 秒；`113606Z` 是脚本自身缺陷导致的失败记录）：20 项检查全部通过。v0.1.10 `agentbox` SHA-256 `8263722725bb…`、v0.1.11 `fc2f67f9f560…`，均来自校验过 SHA256SUMS 的公开 Release 包。环境：Debian 12 x86_64、4 CPU、UID 1000。

| 步骤 | 秒 |
| --- | --- |
| 安装 v0.1.10 / 首次激活 | 0.747 / 1.771 |
| 安装 v0.1.11 | 0.797 |
| 激活 v0.1.11（检查、停服、系统备份、切换、启动、健康检查） | 2.536 |
| 停服 | 0.016 |
| 用 v0.1.11 保留升级后状态（系统备份） | 0.300 |
| v0.1.10 校验兼容备份 | 0.214 |
| v0.1.10 恢复到新目录 | 0.247 |
| 移动用户文件（同一文件系统内 rename） | 0.000 |
| 改写配置并 `check-config` | 0.223 |
| 激活 v0.1.10 | 2.383 |
| **回退合计（停服 → v0.1.10 健康）** | **3.881** |

规模只有 2 个用户、2 个升级前空间、每空间 21 个文件（约 160 KB），没有用量行；计时只说明脚本化步骤本身很快，不代表生产耗时。生产实例（只读查看）数据库约 5 MB + 4 MB WAL，users 8.3 GB，所在 XFS 根分区剩余 6.9 GB；系统备份历史包约 1.4 MB。

演练中确认的三点已写入回退步骤：

- **用户文件只能移动不能复制**：生产 users 大于剩余空间，复制会写满磁盘。系统备份只含用户模板与 MCP 配置，现有 users 树更新，整体移动到恢复目录即可；恢复目录须与原数据目录在同一文件系统。
- **必须先删除会话容器**：`dockerx.EnsureRunning` 复用已有容器时只检查 `/shared` 挂载、镜像和 env，不核对 workspace/home 的挂载源；容器用 `Binds`，源路径不存在时 Docker 会静默创建空目录。数据目录改变后不删除旧容器，空间会挂到旧路径或空目录。
- **恢复配置为相对路径**：`restore` 把 `data_dir`、`cache_dir`、账号凭证改为恢复目录内的相对路径；放回 `/etc/agentbox/config.json` 前须改成绝对路径并用 v0.1.10 `check-config` 验证。

边界：systemctl 为模拟（服务作为子进程运行），Docker API 是只应答 ping、不含容器的桩（实际只收到 `HEAD /_ping`），数据为合成。没有覆盖真实 systemd、容器删除与重建、OAuth 续期、隧道、桌面同步日志或生产规模；生产数据的恢复演练属于 M7-02。
