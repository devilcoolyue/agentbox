# 项目维护与用户体验迭代计划

评估日期：2026-10-05。代码基线：`7df5cf2`。状态：建议排期，尚未开始实施。

目标用户继续以个人自托管和可信小团队为主。接下来五个里程碑围绕「更容易完成第一个任务、日常操作更可靠、问题更容易恢复、维护者更容易发布」展开。

本计划依据源码、CI 配置、用户文档、发布与验收记录制定，没有本轮线上行为数据或用户访谈。体验问题属于有代码依据的改进假设，优先级应在第一期通过用户任务观察校准。历史文档中的验收结果与本次实际执行的检查分别记录，不将历史待办直接当作当前缺口。

## 当前判断

项目已具备完整的工作台、账号池、Git、用量与额度、内网连接和桌面同步能力。维护基础也已建立：业务服务提取、受限文件访问、事务迁移、备份恢复、发布包与兼容回归均有实现。下一阶段最需要的是把已有能力连接成清楚、可恢复的使用流程，并控制多端和上游 CLI 带来的维护成本。

| 观察 | 当前证据 | 下一步价值 |
| --- | --- | --- |
| 测试和发布基础较完整 | `.github/workflows/ci.yml`、`release.yml`、`desktop.yml` 已覆盖多种 Go、浏览器、容器和原生验收 | 整理执行入口、分层和证据，补缺口，而不是重新建设 CI |
| 已有空状态引导，但首个任务仍跨多个入口 | `web/src/home.ts`、`sessions.ts`；README 的首次使用需依次配置账号、创建空间、导入项目、发送任务 | 增加按角色和实际环境状态推进的引导，把项目导入连到创建流程 |
| 已有诊断导出，但主要是静态状态 | `internal/server/diagnostics.go` 输出版本、磁盘、资源和用量同步；`server.go` 的通用错误是 `{error: string}` | 用稳定错误码、操作关联 ID 和分层检查把问题与解决动作对应起来 |
| 已有聊天重连，但发送确认边界仍可加强 | `web/src/chat.ts` 发送后清空输入；`internal/server/chat.go` 的用户消息没有客户端消息 ID 和接收确认字段 | 保存待确认内容、服务端幂等接收、断线后查询执行状态，降低丢输入和误重发风险 |

| 桌面同步已实现且有三平台自动化证据 | `docs/architecture/desktop-client-acceptance.md`、`docs/compatibility.md` | 收尾签名、公证、最低系统、真实输入与升级体验；不重复安排同步引擎开发 |
| 文档状态容易混淆 | 重构计划顶层仍写实施中，阶段清单已勾完；桌面进展记录保留多轮历史待办；排障指南仍有旧部署/网络路径描述 | 明确当前能力、历史记录和部署模式，减少维护者与用户误读 |
| 管理员失联恢复仍需人工维护 | `docs/troubleshooting.md` 明确没有文档化的一键离线重置入口；CLI 当前有配置检查、备份和密钥轮换 | 增加受控的管理员离线密码恢复，避免直接修改数据库 |

## 排期与范围控制

按 1～2 名核心维护者、每期 2～3 周先规划 10～15 周；这是初排，不是交付承诺。第一期结束后按实际工作量、用户反馈和证书/设备准备情况重估。人手不足时顺延里程碑，不压缩验收。

每期预留约 25% 时间处理回归、用户反馈和文档。每个里程碑只承诺下文必做项；可延期项进入候选池，不计入完成条件。责任角色可由同一人承担，但每期开始前要指定实际负责人。

| 里程碑 | 建议周期 | 用户能感受到的结果 | 主要责任 | 依赖 |
| --- | --- | --- | --- | --- |
| M1 故障定位与维护基线 | 第 1～3 周 | 出错知道原因、下一步和如何提供有效反馈 | 后端/维护者 | 无；同时启动 M5 的证书和设备准备 |
| M2 首次使用与项目导入 | 第 4～6 周 | 从登录到第一个任务有连续路径 | 前端/产品、后端 | M1 的错误码与环境检查 |
| M3 日常任务可靠性 | 第 7～9 周 | 输入可恢复，断线后知道任务是否已接收 | 前后端 | M1 的关联 ID；现有历史、用量幂等机制 |
| M4 持续维护与升级质量 | 第 10～12 周 | 升级更可预测，修复不易影响其他功能 | 维护者/后端 | M1 测试清单；M2/M3 的真实改动热点 |
| M5 桌面稳定版与多端一致性 | 第 13～15 周 | 安装、更新和日常操作更顺畅 | 桌面/发布维护者 | 证书、实机和兼容矩阵；M1 错误规范 |

时间表按每期 3 周展示；范围较小时可按 2 周执行。M4 的模块拆分随 M2/M3 开发持续进行，集中验收放在第四期；M5 的外部资源准备从第一期开始。

## M1：故障定位与维护基线

**必做项**

1. 为登录、空间启动、聊天准入等高频失败增加稳定错误码、操作关联 ID 和可执行提示。保留旧 `error` 字段，逐步增加字段；明确可重试、需要重新授权、需要管理员处理等区别。前端按错误码翻译，服务端日志可按同一 ID 定位，不把内部路径或凭证发给用户。
2. 在现有诊断导出和 `check-config` 上增加分层检查：配置、Docker、指定镜像、数据目录权限/磁盘、WebSocket 与账号配置状态。状态区分“通过、失败、未检查”；未调用模型不能显示“模型可用”。普通用户只看自己有权查看的空间结果，管理员看实例级结果。
3. 增加管理员离线密码重置命令：核验目标配置与数据锁、要求服务停止、隐藏输入密码、事务修改并撤销旧令牌，不改变原有额度和空间。文档给出明确的备份和恢复路径。
4. 整理当前能力与测试清单，修正新旧部署、透明/兼容隧道等说明；统一测试入口，标注离线、Docker、原生、付费/人工测试。记录 5～10 次真实任务观察和故障反馈，得到首个任务耗时、失败类型、定位耗时的初始样本。

**验收**

- 至少覆盖 Docker 不可达、镜像缺失、账号撤权、额度不足、磁盘不足、WS 失败等六类合成故障；用户得到明确下一步，维护者能通过关联 ID 找到同一操作。
- 脱敏报告通过白名单与权限测试；没有账号令牌、提示词、文件内容或未授权用户信息。
- 隔离测试实例完成管理员密码恢复，旧令牌失效，空间和账本保持一致。
- 有一份“当前支持什么、如何验证、哪些尚未验收”的权威清单；历史记录保留但不冒充当前状态。

**可延期**：Prometheus 指标端点、外部告警渠道。先记录足以定位问题的结构化事件，不要求部署完整监控平台。

## M2：首次使用与项目导入

**必做项**

1. 管理员首次配置引导串起环境检查、账号接入和默认模型；普通用户引导只展示已授权账号和可用操作。无可用账号时直接说明联系管理员或配置入口，不让用户提交必然失败的创建表单。
2. 创建空间提供“空项目、上传项目、从 Git 导入”三种入口，复用已有上传/Git 连接能力。每步可返回、失败可重试；重试复用已创建空间，不能留下多个半成品容器。
3. 创建时展示最终采用的模型、账号和资源配置；首次进入提供一个可编辑任务示例，并把对话、文件、变更审查和下载/推送串成连续流程。
4. 将“服务端更新、Agent 镜像更新、桌面应用更新”分别标明，显示版本、兼容状态、生效范围和是否需要重新启动空间。沿用现有更新入口，不重新实现更新器。

**验收**

- 找 5 名未参与开发的目标用户观察操作；在服务器和账号已准备好、上游正常的条件下，目标为至少 4 人无需口头指导，在 10 分钟内完成“导入示例项目 → 首次任务 → 查看改动/下载”。这是建议目标，M1 后可校准。
- 管理员与普通用户、无账号、Git 认证失败、上传失败各有回归；返回或重试不重复创建空间。
- 简中、繁中、英文，桌面浏览器与窄屏都可完成关键路径；验证键盘焦点、错误提示和触屏操作。

**可延期**：官方 amd64/arm64 预构建 Agent 镜像与 digest 安装。先验证分发许可、构建发布成本和目标网络可达性，保留源码构建；环境/任务预设先收集需求。

## M3：日常任务可靠性

**必做项**

1. 按实例、用户、空间和线程隔离保存聊天草稿及待确认文本；明确过期、退出清理和禁用本机保存的行为。附件引用单独检查有效性，不能恢复成不存在的路径。
2. 扩展聊天协议：客户端消息 ID、服务端持久接收记录、确认与状态查询。同一 ID 重发不启动第二个回合；确认丢失时先查状态。旧客户端继续工作，新能力通过协商启用。
3. 区分“待接收、已接收、启动中、执行中、已完成、已中断、结果待核对”。浏览器断线不等于任务失败，服务重启后的未知结果不能自动重跑；余额扣减继续沿用现有用量与账本事务。
4. 增加空间名称搜索和运行/休眠/停止筛选；保留已有最近空间及线程标题搜索，先解决空间增多后难以找到项目的问题。

**验收**

- 覆盖快速双击、发出后断网、确认丢失、刷新、多标签、切换线程、退出重登、服务重启；同一已接收消息只启动一个回合，不因客户端重试重复执行或重复扣款。
- 草稿与附件不串用户/空间/线程；失败后可以查看并恢复自己的未确认内容。
- “结果待核对”有明确恢复入口，不把服务重启后的不确定状态显示为成功。
- 100 个空间的合成数据下搜索、筛选与切换可用；性能阈值按 M1 约定的设备测量。

**可延期**：收藏、归档、全文搜索、系统任务完成通知。归档必须先定义与停止、删除、保留磁盘文件的区别。

## M4：持续维护与升级质量

**必做项**

1. 根据 M2/M3 实际热点继续拆分聊天的输入、流式渲染、回合状态与历史恢复，以及设置页的独立功能。逐步收窄共享状态，让模块拥有初始化、请求取消和销毁边界。后端将聊天执行编排从 HTTP/WS 层提取，沿用现有 workspace/credentials/usage 服务。
2. 为本轮新增的错误和聊天协议建立可版本化 schema/契约样本与 Go/TS 一致性测试；将能力发现、兼容窗口和淘汰规则写进一张多端矩阵。优先覆盖频繁变动的接口，不一次性重写全量 API。
3. 在已有 CI 上明确快速 PR 检查、关键链路 Linux 集成和发布前完整验收三层。并发/生命周期改动增加定向 race；把散落脚本纳入可发现的入口，保留失败报告，并要求每个实际缺陷补行为回归。
4. 对 Agent 镜像更新补合成上游协议冒烟：握手、续聊、中断、用量解析和必要 MCP 行为。先提供候选验证结果再切换；自动跟随也必须通过门槛，失败保持原镜像。发布包验收同时验证迁移、系统/完整备份恢复和回退限制。

**验收**

- API/WS 兼容测试和旧客户端回归通过；新业务服务不反向依赖 HTTP 包。
- 模拟 CLI 事件格式变化或握手失败时，候选不能通过验证；未知用量保留可定位告警，不静默当作完整正常计费。
- 干净 Linux 测试环境完成升级、重启、备份验证和恢复到新目录；真实 systemd 与模拟测试分别记录。不能直接用旧二进制打开更高 schema。
- 在声明的数据规模下记录恢复用时、备份间隔和丢失窗口，并与实例管理员约定 RTO/RPO；系统备份不含项目文件的限制必须醒目说明。
- 固定 runner 上记录 PR 检查耗时与非确定性失败率；初始目标为快速检查 10 分钟内、连续 20 次执行无非确定性失败，完整矩阵单列。

**可延期**：全量 OpenAPI/客户端生成、长对话虚拟列表、首页汇总 API。先用性能与维护数据证明收益，避免为代码行数做机械拆分。

## M5：桌面稳定版与多端一致性

**必做项**

1. 接入并验收 Apple Developer ID、公证和 Windows 代码签名；验证正式签名安装包、真实旧包升级和应用内更新。更新签名与 OS 签名分开验收，核对凭证库、目录绑定、同步基线和恢复记录的延续。
2. 补最低支持系统和真实设备场景：中文输入法候选窗、Finder/Explorer 拖放、高 DPI/多屏、休眠恢复、常见安全软件、真正无 WebView2 的离线 Windows。依据测试结果确定支持下限。
3. 单独交付桌面三语版本，沿用已实现的语言功能；统一网页与桌面的空间状态、错误解释和版本说明，保留各自适合的操作方式。
4. 通过少量自愿试用者开展有退出条件的同步试用，记录冲突、恢复、支持请求和版本组合。同步继续由管理员明确开启，客户端确认目录与计划；发布不自动更改生产配置。

**验收**

- 支持矩阵中的系统和架构有正式安装、升级、凭证延续与恢复报告；缺证书或实机证据时继续标记测试版，不宣布稳定版完成。
- 真实设备上完成输入、传输、休眠重连、同步冲突恢复；内容哈希、恢复副本和绑定状态符合预期。
- 发布、升级和回退说明清楚区分服务端 schema、桌面本地 schema、Agent 镜像；旧网页和 abox-link 兼容回归仍通过。
- 小范围试用至少持续一个完整迭代周期，未解决的数据丢失、权限越界、重复扣费、启动失败问题阻止稳定发布。

**可延期**：更多操作系统/架构、外置磁盘同步、超大文件与更多同步模式。证书或设备准备不足时顺延稳定版，先交付明确标注边界的测试版。

## 持续跟踪与取舍

优先跟踪六项指标：首个任务完成率与耗时、空间启动失败率、错误定位耗时、消息状态不明/误重发次数、每活跃用户支持请求、发布后回归数。按版本、网页/桌面及失败类型区分；模型上游耗时与本地启动耗时分开，收费数据沿用已有口径。

默认用本实例聚合计数和用户自愿反馈，问题记录不附提示词、代码、凭证或原始文件。不为得到指标自动上传使用内容；不把小样本的改善比例当作已证实结论。

暂不安排微服务/Kubernetes、多节点调度、整个网页框架替换、多人实时共同编辑、更多 Agent 接入或不可信公网多租户。这些方向都扩大维护面；待现有用户需求与容量数据支持后再单独立项。Git、MCP、隧道和同步已有能力优先补连贯使用流程与缺陷。

每期结束按同一顺序评审：演示完整用户任务、核对验收报告、查看反馈与指标、决定发布或继续修复。优先级依次为数据/权限/计费正确性、阻断用户使用的问题、体验改进、扩展功能。
