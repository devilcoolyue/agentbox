# 第二轮里程碑计划：收口、真实验收与维护成本

评估日期：2026-10-06。代码基线：`83be87d` 之上的开发工作树（264 个未提交路径，136 个已跟踪文件 +5160/−3870），生产实例运行开发版 `v0.1.11-dev.milestones.20261006.1`，正式发布仍为 v0.1.10。第一轮计划 [M1～M5](roadmap.md) 及其记录（[m1](milestones/m1.md) / [m2](milestones/m2.md) / [m3](milestones/m3.md) / [m4](milestones/m4.md) / [m5](milestones/m5.md) / [交付](milestones/delivery-20261005.md)）原样保留，不再改写；本文接续编号 M6～M10。

## 第一轮复盘

26 个实施单元中 19 个软件开发完成并通过本地自动化，1 个部分交付（M5-03 本地测试包），6 个被外部资源卡住（M1-06/07、M2-05、M5-01/02/04）。按原验收标准没有一个里程碑可宣布完成。三个结构性原因：

| 原因 | 证据 | 第二轮对策 |
| --- | --- | --- |
| 外部资源从未启动 | 负责人、参与者、证书、设备、RTO/RPO 在 15 周里始终为“待落实”；软件完成度掩盖了验收完成度为 0 | 外部资源单列为并行轨道，有周检查点；M8 范围由 M7 真实样本决定，没有样本不开新功能 |
| 开发版先于正式发布进入生产 | 264 个未提交路径已部署授权实例；无 tag、托管 CI 新增工作流（chat-reliability、recovery-drill、verification-stability、release 候选门槛）一次都没在远端跑过；回退只能依赖兼容备份 | M6 第一优先级是提交、托管 CI 跑通、发布 v0.1.11 正式版 |
| 计划要求跟踪六项指标，但没有采集机制 | 代码中没有任何指标聚合或导出；首任务耗时、启动失败率、状态不明次数只能靠人工翻日志和 SQLite | M7 增加实例内聚合计数与脱敏导出，先有数据再谈改善 |

其余已确认的事实：Agent 镜像基线仍是 Claude 2.1.280 / Codex 0.145.0，Codex 0.156.1 候选已通过 11 项门槛但未推进；安装仍需现场构建镜像；`web/src/types.d.ts` 1075 行手工对齐，契约生成只覆盖 chat-errors；生产实例已有 18～19 个空间，两条真实界面反馈（引导占位、输入区紧凑化）均已修正。

## 排期与范围控制

仍按 1～2 名核心维护者、每期 3 周规划 15 周；这是初排，不是交付承诺。每期预留约 25% 处理回归、反馈和文档。每个里程碑只承诺必做项，可延期项进入候选池。

| 里程碑 | 周次 | 用户能感受到的结果 | 主要责任 | 依赖 |
| --- | --- | --- | --- | --- |
| M6 收口与正式发布 | 1～3 | 用的是有版本号、可回退的正式版，不是未提交的开发版 | 维护者 | 无；外部资源轨道同时启动 |
| M7 真实使用验收与指标基线 | 4～6 | 问题有数据可查；首任务耗时、失败类型有真实样本 | 后端 + 观察负责人 | M6 正式版；参与者到位 |
| M8 反馈驱动的日常效率 | 7～9 | 真实观察中的高频阻断被修复；空间多了也好找 | 前后端 | M7 样本与指标；无样本则缩为维护项 |
| M9 上游追新与安装成本 | 10～12 | 安装更快，CLI 更新更可预期，依赖更安全 | 维护者 | M6 托管 CI；许可核对结果 |
| M10 桌面稳定版 | 13～15 | 签名安装包、正式升级、试用周期完成 | 桌面/发布维护者 | 证书与实机；第 6 周检查点决定是否降级 |

## 发布节奏与版本规则

第一轮把 15 周的改动攒成一个未提交、已上生产的开发版。第二轮用以下规则防止重演：

- 每个里程碑结束发布一个正式版（预期 v0.1.11 → 0.1.12 → 0.1.13 → 0.1.14 → 0.1.15），patch 版本只修缺陷不加功能。里程碑内的中间构建只能以 `-dev.<标识>` 版本部署到授权实例，且必须先提交推送。
- schema 变更只能随正式版发布，发布前 `docs/compatibility.md` 写明旧二进制能否打开、回退需要哪个 schema 的兼容备份；同一正式版最多提升一次 schema。
- 服务端 / abox-link 同版本号，桌面独立编号（现为 0.1.3-dev），Agent 镜像按 `versions.env` 基线记录；三者的对应关系在 `releases.md` 一张表里维护。
- 正式发布前的固定门槛：托管 CI 绿、`test-release.py` / `test-release-server.py --restart` 通过、核心场景 Chromium + WebKit 浏览器回归通过、一次显式付费真实 provider 冒烟记录、从上一正式版的升级与回退（兼容备份恢复到新目录）各演练一次。

## 风险与假设

| 风险 | 影响 | 触发信号 | 应对 |
| --- | --- | --- | --- |
| Anthropic / OpenAI 收紧第三方 OAuth 或 CLI 非交互使用政策 | 账号池、`claude -p` / `codex app-server` 链路失效，产品核心不可用 | 新版 CLI 拒绝 OAuth 凭证播种、provider 公告、账号被封 | M4-04 门槛阻止切换；保留 API Key 接入路径；公告时在 README 明示边界；不自动升级 CLI |
| CLI 协议/事件格式变化快于每月例行 | 用量漏记、回合状态误判、`usage: … 未记到用量` 告警 | 候选门槛失败、告警出现 | 门槛失败不切换；告警当缺陷处理并补 testdata 样本 |
| 签名证书审批周期不可控 | M10 不能称稳定版 | 第 3/6 周检查点仍无证书 | 降级规则已定；时间吸收 M8/M9 溢出 |
| 单维护者 | 任一里程碑停摆，外部轨道无人跟 | 连续两周无提交或检查点无记录 | 顺延不压缩验收；外部轨道负责人可独立于代码维护者 |
| 生产实例单点、无人值守 | 故障发现靠用户反馈 | `/ping` 失败无人知晓 | M7 加外部存活探测；M7 恢复演练约定 RTO/RPO |
| 浏览器回归只有 Chromium | Safari/iOS 专属问题继续靠真机偶然发现 | AGENTS.md 已记录十余处 Safari/iOS 特判 | M6 起核心场景加 WebKit；真机仍为 M10 实机项 |
| 真实用户样本仍为 0 | M8 回到按假设排优先级 | 第 6 周检查点样本 <5 | M8 范围规则已定，只做已知反馈与维护项 |
| 每接一个 Agent 都带来一整套维护面 | 凭证格式、事件解码、用量解析、终端 transcript、门槛 probe、价格条目各一份；上游改格式时按 Agent 数倍增 | 某 Agent 门槛连续失败或用量告警持续 | M11 只接满足最小能力集且有稳定 headless 协议的 Agent；优先 ACP 等共享协议；不达标的停留在候选 |

假设：目标用户仍是个人自托管与可信小团队；维护者 1～2 名；生产实例规模在数十空间、个位数用户量级；上游 CLI 继续提供可脚本化的非交互模式。任一假设失效时重估计划，不在里程碑内硬扛。

## M7：真实使用验收与指标基线

**必做项**

1. 实例内聚合指标，只计数不存内容：首任务完成数与耗时（创建收据时间 → 该空间首个 completed 回执）、空间启动失败按错误码、消息回执 uncertain / 显式重试 / 放弃次数、回合 `wall_ms` / `ttft_ms` 分布（已有用量表）、每用户空间数与磁盘占用（复用现有 storage 接口），按版本与网页/桌面区分。管理员页展示并提供脱敏 JSON 导出；可选 Prometheus 文本端点，仅 admin token，不引入新依赖。
2. 执行第一轮欠下的外部验收：M1-06 的 5～10 次真实任务/故障观察、M2-05 的 5 名用户首任务观察、M3-04 性能设备与阈值确认、M4-05 的 RTO/RPO 约定，以及对生产数据的一次恢复演练（恢复到新目录，不动生产实例）。
3. 若观察显示按操作编号定位慢，增加管理员按 `operation_id` 查关联日志与回执的只读入口；否则不做。
4. 生产实例外部存活探测：用一个外部 uptime 服务按分钟探测 `/ping`，失败通知维护者；只探测公开健康端点，不传令牌。这是零代码项，但要写进 `deploy/README.md` 并记录接入日期。

**验收**

- 指标页能直接回答六项跟踪指标中至少四项，数值与 SQLite 直接查询一致；导出通过白名单测试，不含提示词、路径、凭证。
- 观察样本 ≥5，得到首任务耗时、失败类型、定位耗时的分布，写入 observations.md；M8 候选池按此排序。
- 生产数据恢复演练完成，实际 RTO 与备份间隔写入 `deploy/README.md`，与管理员确认。
- 外部存活探测已接入并至少触发过一次人为停服测试通知。

**可延期**：更多告警渠道与阈值告警；每活跃用户支持请求的自动统计（先人工记）。

## M8：反馈驱动的日常效率

**范围规则**：第 6 周检查点从候选池选取。观察样本 <5 时只做第 1 项已知反馈与维护项，不开新功能。

**候选池**

1. 修复 M7 观察中的前 3 类阻断或高频问题（必做，具体内容待观察结果）。
2. 空间归档：先定义与停止/删除/磁盘保留的区别——归档空间不出现在默认列表与容量检查、文件与线程保留、可恢复；处理桌面同步绑定与账号授权状态。
3. 任务完成通知：复用回执状态，页面标题/favicon 徽标 + 用户显式授权的浏览器 Notification；桌面原生通知；正文默认不进系统通知。
4. 长对话虚拟列表或历史分页：仅当 M7 的线程长度与渲染数据证明需要。
5. 首页汇总 API：仅当百空间性能或 M7 指标显示首页加载成为问题。
6. 聊天历史导出：按线程导出 Markdown 与原始 JSONL，属主限定、走 `safefs` 读取、附件以引用列出不打包正文外文件。依据：对话记录只在 `users/<user>/sessions/<id>/chats/` 下，系统备份不含它，用户目前没有自助带走数据的入口。
7. 每用户空间数 / 磁盘上限：配置中目前只有费用额度，没有空间数量或磁盘上限。先靠 M7 指标看每用户磁盘占用；需要时增加管理员可设的软上限，到限只阻止新建与上传并提示，不自动删除。

**验收**

- 每项有简中/繁中/英文浏览器回归与窄屏截图；归档不删除文件、不改变账本与用量；通知在拒绝授权时静默降级。
- 导出只包含请求者自己的线程，不跟随链接，不含其他用户或实例信息；上限触达只拒绝新写入，不影响已运行回合。
- 处理的阻断问题在 M7 同一观察口径下复测，记录改善前后样本，不用小样本比例作结论。

## M11：多 Agent 接入

**“插件化”的实际含义**。服务端是 Go 单二进制，Agent CLI 装在会话镜像里，而凭证文件格式、事件流、用量字段、终端 transcript 都必须由服务端代码理解，所以做不成运行时热插件。可行且用户能感知的形态是：**编译期 Provider 注册表 + 镜像可选安装 + 管理员在账号池选择类型**——镜像装了哪些 CLI，账号池和创建弹窗就能选哪些。每个 Agent 的能力位（OAuth 续期、MCP 管理、技能市场、app-server 真流式等）各不相同，界面按能力位显示，不假装所有 Agent 等价。

**候选 Agent 现状**（2026-10-07 查证，后续以实测为准）

| Agent | 分发 | headless 与结构化输出 | 凭证 | 结论 |
| --- | --- | --- | --- | --- |
| Kimi Code CLI（`@moonshot-ai/kimi-code`） | npm，Node ≥22.19 | `-p --output-format stream-json`；`--session` 恢复；`kimi acp` JSON-RPC | `kimi login` 设备码流程（headless 打印 URL），或 config.toml API Key | **首个接入**：分发方式与现有 Dockerfile 一致，两种协议可选，文档完整 |
| DeepSeek Harness `dsh`（`@deepseek-ai/dsh`） | npm，开源 | `dsh --profile headless "job"` 打印最终答案；ACP 由第三方 `@openma/deepseek-harness-acp` 提供；官方结构化事件流仍在演进 | `DEEPSEEK_API_KEY` 或 `/auth login` | 候选：等官方 ACP 或结构化流稳定后接入 |
| Antigravity CLI（`agy`） | 闭源 Go 二进制，curl 安装脚本 | TUI 为主；headless 仅 `GEMINI_API_KEY` + `modelProvider=gemini`；未见 JSON 输出文档 | Google 账号或 Gemini API Key | 观望：无结构化输出就无法做回执/用量；需要 ACP 或官方 JSON 模式 |
| ZCode（Z.ai） | 专有桌面应用，非 CLI | 仅社区 `zcode-cli` 包装 | GLM Coding Plan | 排除：不是受支持的 CLI 产品 |

**必做项**

1. ACP（Agent Client Protocol，JSON-RPC over stdio）客户端传输作为 `internal/agent` 的第三种传输，与现有 Claude stream-json、Codex app-server/exec 并列；事件统一映射到 `agent.Event`（Output / Partial / SessionID / Terminal），中断走协议内 cancel，握手失败时的回退规则与 Codex 一致（只有回合提交前失败才可回退）。一次实现可接 Kimi、dsh 及后续任何 ACP Agent。
2. 首个新 Agent：Kimi Code CLI。镜像可选安装；账号类型 `kimi`，凭证支持 API Key（写 config.toml）与 `kimi login` 产生的令牌文件播种两种；`stream-json` 与 ACP 以容器内实测择一为主；`--session` 恢复；`SeedDefaultModel` 写入其配置；用量按实测事件解析，字段缺失时该回合标“未计量”并打现有 `usage: … 未记到用量` 告警，不静默按 0 扣款。
3. 每个 Agent 的最小能力集与交付清单：headless 聊天 + 流式事件 + 会话恢复 + 用户中断；凭证播种；默认模型写入；用量解析或显式“未计量”；`agentprobe` 合成驱动器与门槛检查；价格目录条目；三语文案；`docs/accounts-and-models.md` 中该 Agent 的能力矩阵。Claude 专属能力（OAuth 自动续期、MCP 管理、技能市场、HUD）不作为接入门槛，界面按能力位隐藏。终端内运行任何 CLI 都是免费获得的，不计入接入工作。
4. 镜像构建参数 `AGENTBOX_AGENTS`（默认 `claude,codex`，行为不变），`versions.env` 按 Agent 记录版本；未安装的类型在账号池、创建弹窗、默认模型设置中不可选；`/api/onboarding` 与 `/api/updates/components` 报告已安装 Agent 与版本；候选镜像门槛按已安装 Agent 逐个运行。

**验收**

- Kimi 在真实容器内完成：创建空间 → 网页对话（流式、中断、`--session` 恢复）→ 终端运行 → 用量入账或显式未计量；两种凭证方式各一次。
- 门槛：Kimi 的合成驱动器覆盖与 Claude/Codex 等价的握手、续聊、中断、用量、未知格式失败；格式变化时候选不能切换。
- 现有 Claude/Codex 全部回归不变；`AGENTBOX_AGENTS` 缺省构建的镜像与之前字节级等价或差异可解释。
- 文档给出每个 Agent 的能力矩阵与明确不支持项；README 双语说明“可选 Agent 取决于镜像”。

**可延期**：dsh 接入（等官方 ACP/结构化流）；Antigravity（等 JSON 输出）；配置驱动的“声明式 stream-json Agent”（无用量/凭证理解，收益存疑）。

## 持续跟踪与取舍

六项指标不变：首个任务完成率与耗时、空间启动失败率、错误定位耗时、消息状态不明/误重发次数、每活跃用户支持请求、发布后回归数。M7 之后前四项由实例内聚合提供，后两项继续人工记录。
